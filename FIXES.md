## Фикс 3 — не уведомлять и не показывать «Сообщить» если резидент сам занял своё место

**Файл Flutter:** `lib/pages/guests_page.dart`
**Коммит Flutter:** `f15ddff`
**Бэк:** **изменений не потребовалось** (логика уже корректна, см. ниже).

### Что сделано на фронте
Раньше `_myActivePassSpotIds` объединял пропуска со статусами `active` + `arrived`
— из-за этого даже после законного приезда гостя место в сетке показывалось
как «моё занятое» и предлагало «Сообщить администратору».

Теперь разделено на два множества:
- `_pendingPassSpotIds` — только статус `active` (QR ещё не сканировали).
- `_arrivedPassSpotIds` — только статус `arrived` (гость уже на территории).

Логика тапа по красному месту в сетке:
- Если место в `_pendingPassSpotIds` → диалог «Гостевое место занято / Сообщить администратору».
- Если место в `_arrivedPassSpotIds` → снэкбар «Место занято вашим гостем (на территории)», без диалога.

### Почему на бэке ничего не делали (от Backend Claude, дословно)

> Логика уже корректна (`client.go:421-435`): для permanent-места при occupied
> бэк проверяет был ли barrier_event с машиной владельца через parking-gate за
> последние 30 минут. Если был — push не шлётся.
>
> Симптом «ложных пушей при симуляции» — это не баг бэка, а неполная симуляция.
> Текущий Node-RED parking flow шлёт только `{spot_number, event_type}`, никакого
> car_number в payload нет. В реальной жизни машина владельца не может
> оказаться на permanent-месте, не проехав через ворота. При симуляции Мансур
> инжектит сразу parking occupied без предварительного barrier-gate IN —
> поэтому бэк справедливо считает машину чужой.

### Как протестировать (правильный сценарий симуляции)

**Сценарий C (positive — владелец на своём permanent-месте):**
1. Открыть Node-RED → вкладка **Barrier**.
2. Инжект **Manual IN** с номером владельца (например `A777BC`).
   - ⚠️ Проверить, что `gate_id = parking-gate`, а **не** `main-gate`. Если такого инжекта нет — попросить Егора добавить.
3. Подождать **30 секунд** (бэк регистрирует barrier_event).
4. Node-RED → вкладка **Parking Simulator** → **Permanent spot occupied P-01** (где `P-01` закреплено за владельцем `A777BC`).
5. ✅ Push **НЕ приходит**, в истории уведомлений ничего нового.

**Сценарий D (negative — чужак на permanent-месте):**
1. Без предварительного barrier IN дёрнуть **P-01 occupied**.
2. ✅ Приходит push с `kind=parking_alert` (оранжевая иконка `local_parking`).

**Сценарий E (UI фронта — гость уже приехал):**
1. Создать пропуск на `G-01`.
2. QR-скан (статус `arrived`).
3. Открыть страницу «Гости» → форма создания → сетка гостевых мест.
4. Место `G-01` красное (занято).
5. Тапнуть на `G-01`.
6. ✅ Появляется снэкбар «Место G-01 занято вашим гостем (на территории)».
7. ✅ Диалог «Сообщить администратору» **НЕ появляется**.

### Что реализовано на бэке (от Backend Claude, c3309ca)

- Миграция `014_staff_profile_fields.sql` — добавляет `profiles.work_schedule VARCHAR(255)` и `profiles.description TEXT`. Применится автоматически при следующем старте бэка.
- `POST /api/v1/admin/staff`:
  - Только `role=admin`.
  - Валидация: email-формат, password ≥ 6, specialty из 6 значений.
  - bcrypt-хэш пароля, `INSERT INTO users + profiles` в одной транзакции.
  - Созданному сотруднику ставится `role='staff'`, `verification_status='approved'` (не висит в очереди верификации).
  - `409 Conflict` на дубликат email, `201 Created` с телом созданного сотрудника.
- **Логин сотрудника работает из коробки**: `POST /auth/login` с email/паролем → JWT с `role='staff'`. Никаких отдельных staff-auth эндпоинтов не нужно.
- **Фронт уже поддерживает роль `staff`** (`dashboard_page.dart:148-198`): сотруднику показывается дашборд с 2 вкладками — «Заявки» (ServiceRequestsPage) и «Профиль» (ProfilePage). Никаких правок Flutter после Backend-фикса не потребовалось.

### Контракт API (зафиксирован)

**Эндпоинт:** `POST /api/v1/admin/staff`
**Авторизация:** только роль `admin` (как `GET /admin/staff`).
**Content-Type:** `application/json`

**Тело запроса:**
```json
{
  "full_name": "Ахмет Бекжанов",
  "email": "plumber@test.com",
  "password": "12341234",
  "phone": "+7 701 234 5678",
  "specialty": "plumbing",
  "work_schedule": "Пн–Пт, 09:00–18:00",
  "description": "Устранение протечек, ремонт кранов и труб."
}
```

**Ожидаемое поведение бэка:**
1. Валидация: все поля кроме `description` — обязательные.
2. Проверка уникальности `email` (если занят — 409 `{"error":"email_taken"}`).
3. Проверка `specialty` ∈ {`plumbing`, `electrical`, `cleaning`, `garbage`, `intercom`, `elevator`} (иначе 400).
4. Хэширование пароля (bcrypt, как у обычных юзеров).
5. Создание записи в таблице сотрудников (`profiles` с `role='staff'` + специализация в отдельной таблице/колонке — на твоё усмотрение, главное чтобы `GET /admin/staff` сразу её увидел).
6. Возврат **201** с телом созданного сотрудника в том же формате, что отдаёт `GET /admin/staff` (для удобства; фронт сейчас не использует тело, делает `_load()` повторно — но всё же).

**Что важно:**
- Созданный сотрудник должен **сразу залогиниваться** обычным `POST /auth/login` с `email`+`password` (как и предусмотрено в форме «Email для входа»).
- В таблице сотрудников должны быть колонки `work_schedule` и `description` (если их ещё нет — миграция). Их отображение в `GET /admin/staff` и в `services_page.dart` — отдельная задача (см. «Опциональное продолжение» ниже).

**Возможные коды ответов:**
- `201 Created` — успех
- `400 Bad Request` — невалидная специальность, кривой email, короткий пароль
- `409 Conflict` — email уже занят
- `403 Forbidden` — не админ

### Опциональное продолжение (если останется время)

Сейчас `services_page.dart` использует **захардкоженный массив `_kServices`** с данными сотрудников (`staffName`, `phone`, `hours`, `description`). Это значит, что новые сотрудники, добавленные через форму, **не попадут** на вкладку «Сервисы» у резидента, пока этот список не переедет в API.

**Что нужно сделать (отдельная задача):**
1. Бэк добавляет эндпоинт `GET /services` (или возвращает поля `work_schedule`, `description`, `phone` в существующем `GET /admin/staff` и/или `GET /staff`).
2. Фронт меняет `_kServices` в `services_page.dart` на загрузку из API.

Это **не блокер для защиты** — для демо комиссии достаточно показать, что админ может добавить сотрудника через форму, и он появится в списке `GET /admin/staff` (вкладка «Сотрудники» в админ-панели).

5. ✅ Открылась форма «Новый сотрудник».

## Фикс 5 — динамический список сотрудников на странице «Сервисы» ✅ ГОТОВ

**Файлы Flutter:**
- `lib/services/staff_service.dart` (новый)
- `lib/pages/services_page.dart` (переписан)

**Коммит Flutter:** `204694c`
**Файл бэка:** `internal/handler/staff.go` (хэндлер `PublicList`)
**Коммит бэка:** `c3309ca`

### Контекст
Раньше на вкладке «Сервисы» у резидента отображался захардкоженный список сотрудников (`_kServices` в `services_page.dart`). Добавление сотрудника через Фикс 4 не отражалось на этой вкладке. Этот фикс делает список сервисов динамическим.

### Что сделано на фронте

1. **`lib/services/staff_service.dart`** — новый сервис с моделью `StaffMember` и методом `getStaff()` (дёргает `GET /staff`).
2. **`lib/pages/services_page.dart`** переписан:
   - `ServicesPage` теперь `StatefulWidget` с `_load()`.
   - UI-метаданные (название карточки, подзаголовок, иконка, категории заявок) остались в коде в карте `_kSpecialtyMeta` (индекс — `specialty`).
   - Живые данные (ФИО, телефон, режим работы, описание) подтягиваются из API.
   - Маппинг: для каждой специальности из `_kSpecialtyMeta` берётся **первый** сотрудник этой специальности из ответа `/staff`. Если нет — карточка показывается с надписью «Сотрудник не назначен», `available=false`, телефон/часы — прочерк.
   - Если запрос упал — fallback: все карточки как «не назначен» + жёлтый баннер с текстом ошибки.
   - Добавлен `RefreshIndicator` (свайп вниз).
3. **Карточка «Охрана»** оставлена статичной (`_kSecurityService`) — у неё нет отдельной специальности, она информационная.

### Что реализовано на бэке (от Backend Claude, c3309ca)

- `GET /api/v1/staff`:
  - Авторизация: любой авторизованный пользователь.
  - Возвращает массив `publicStaffMember` ровно в формате `StaffMember.fromMap`.
  - **`is_available` вычисляется автоматически**: `true` если у сотрудника нет заявок со статусом `in_progress`, иначе `false`. Поле не хранится в БД, обновляется само при назначении/закрытии заявок админом.
- Разные хэндлеры `/admin/staff` (со счётчиками `in_progress_count` / `done_today_count`) и `/staff` (с `work_schedule` / `description` / `is_available`) — это интенционально, не дублирование.

### Контракт API (зафиксирован)

**Эндпоинт:** `GET /api/v1/staff`
**Авторизация:** любая авторизованная роль (резидент, owner, tenant, staff, admin). Не путать с `GET /admin/staff` — тот только для админа и отдаёт счётчики заявок.

**Ответ — массив объектов с полями:**
- `id` — UUID сотрудника
- `full_name` — ФИО
- `email` — почта (нужна для контакта; фронт её не отображает, но контракт пусть будет полный)
- `phone` — телефон
- `specialty` — одно из `plumbing` / `electrical` / `cleaning` / `garbage` / `intercom` / `elevator`
- `work_schedule` — строка вида «Пн–Пт, 09:00–18:00»
- `description` — описание зоны ответственности (может быть пусто)
- `is_available` — bool, доступен ли сотрудник сейчас (можно вычислять — например `true` если у него нет активных заявок, либо вернуть просто `true` для MVP)

Формат полей совпадает с тем, что фронт уже использует (`StaffMember.fromMap`).

### Как протестировать (когда бэк готов)

1. Залогиниться админом, открыть «Сотрудники», добавить нового сотрудника специальности `electrical` (например `Иван Тестов`, `Пн–Пт, 09:00–18:00`).
2. Логаут → логин резидентом.
3. Открыть вкладку «Сервисы» → раздел «Службы ЖК».
4. ✅ Тапнуть «Электрик» → на детальной странице видны **актуальные** ФИО / телефон / часы добавленного сотрудника, описание и статус «Доступен».
5. На бэке временно убрать сотрудника специальности `plumbing`.
6. Свайп вниз для обновления.
7. ✅ Карточка «Сантехник» показывает «Сотрудник не назначен», серая точка «Недоступен».
8. **Edge case:** выключить бэк, открыть «Сервисы».
9. ✅ Все карточки в режиме «не назначен», сверху жёлтый баннер «Не удалось загрузить сотрудников».
